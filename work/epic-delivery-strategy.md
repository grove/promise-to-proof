# Acceptance contract: Independent, grouped, and mixed epic delivery

Contract revision: v1
Source: [Epic delivery strategy specification](../plans/epic-delivery-strategy-spec.md)
Source attribution: [Issue #33](https://github.com/grove/promise-to-proof/issues/33), imported at update `2026-09-26T21:33:35Z`. The authoritative specification is at commit `5e369c1b45ba817b8add6b20a9b7b1c97898fa12`, SHA-256 `7a231d84f739a459f770870d23038fbc4946c759f04241c87f2a6322d9a1645e`.
Parent: None
Prerequisites: None for parent acceptance planning. Delivery requires the independent verification capabilities already required by the shared protocol.

Intended outcome: Users can deliver an epic's children independently, through one integration branch, or in a mixture of both, and revise that strategy after work starts. Existing workflows recover the approved destinations, preserve work and authority boundaries, and require verification of the assembled parent outcome.

Advisory learnings: None. No advisory learning register is present.

## Evidence procedure

Extend the existing human-runnable conventions in `checks/slice-contract-scenarios.md`, `checks/deliver-issue-scenarios.md`, `checks/implement-contract-scenarios.md`, `checks/review-implementation-scenarios.md`, `checks/publish-pr-scenarios.md`, and `checks/merge-readiness-scenarios.md`. These are public skill invocations, not keyword searches over instruction text. Reference the source S IDs when distributing cases across those files. S IDs may cover several rows without duplicating the requirement store.

For each case, prepare a disposable Git repository with explicit parent/child agreements, known commit trees, approved or deliberately missing plans, and the stated authority. Invoke the relevant installed skill with the request and fixture inputs while withholding expected outcomes. Use a controlled tracker fixture that records actual tool requests and maintains inspectable PR state. Inject changed targets, lost responses, partial success, or concurrent edits at the named operation. Expected destinations, allowed effects, and parent outcomes come from the source scenario and fixture facts, not the implementation's decision logic.

Retain the request, installed skill revision, host/context identity and permissions, exact agreement and candidate identities, full comparison-base SHA, plan text/revision/hash, initial state, action log, resulting state, and observed assertions. Inspect Git trees and refs directly for S8/S13 and controlled tracker state and readback for retargeting/retry cases. Preserve relevant history and transfer records, then run restart variants in fresh contexts with only the child path. Keep evidence outside the product candidate under `.p2p/work/epic-delivery-strategy/` using protocol retention rules.

Mark each run observed pass, observed failure, or unexecuted. A simulated tracker establishes behavior against that controlled interface, not live GitHub compatibility. Record live-service validation separately and leave unavailable live cases explicitly unexecuted. Retain actual successful and rejected mutation observations for controlled cases; textual walkthroughs alone do not satisfy R21/R22/R30.

Inspect shipped protocol distribution paths during implementation, including generated or linked copies, and compare their resolved bytes with `docs/acceptance-contract-protocol.md`. Reuse existing repository checks where relevant. Static consistency checks supplement behavior runs; they do not replace them. Planning runs no acceptance proof.

## Out of scope

- Automatic merges; new tracker labels or tracker requirements; repository-hosted policy enforcement outside the skills; release orchestration; new feature-flag systems; stacked PRs; cross-repository delivery; multiple integration groups per parent; a new scheduler.
- Strategy changes do not authorize reverting published work, deleting branches, force-pushing, or weakening review, proof, CI, compatibility, safety, or authorization gates.
- This planning invocation does not create the child breakdown, implement the feature, create or switch branches, commit, publish PRs, or merge. Those workflows retain their own authority rules.
