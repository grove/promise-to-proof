# Contributing

Thanks for your interest in improving this project. We really appreciate people taking the time to report problems, share ideas, investigate behavior, and help make the project better.

We use an **issue-first contribution model**.

The best way to contribute is usually to start with a GitHub issue so we can understand the problem and agree on the right direction before anyone spends time implementing a solution.

**Please wait for a maintainer invitation before opening a pull request.**

## Why we work this way

Writing code is only one part of maintaining a project.

Before making a change, we usually need to understand:

- what problem needs to be solved;
- whether the change fits the project's goals;
- how it should behave;
- what compatibility or maintenance costs it may introduce; and
- whether there is a simpler solution.

Starting with an issue gives everyone a chance to build that shared understanding first.

A thoughtful bug report, reproduction, investigation, API suggestion, or description of a real-world use case can be just as valuable as a patch.

## Reporting a bug

Please search existing issues first in case the problem has already been reported.

When opening a bug report, include whatever information you have that helps us understand and reproduce the problem.

Useful details may include:

- a clear description of the problem;
- what you expected to happen;
- what actually happened;
- steps to reproduce it;
- a small reproduction or example;
- the version of this project you are using;
- relevant platform, runtime, or dependency versions; and
- logs or error messages.

Small, focused reproductions are especially helpful.

You do not need to know the cause of the problem or provide a fix before reporting it.

## Suggesting an improvement

We welcome ideas for improvements.

When possible, start by explaining the problem or use case rather than jumping straight to a particular implementation.

It is helpful to describe:

- what you are trying to accomplish;
- why the current behavior is difficult or limiting;
- who might benefit from the change;
- an example of how you would use it;
- any workarounds you currently use; and
- any important constraints you know about.

You are welcome to suggest a possible solution too, but you do not need to design the implementation for us.

Sometimes maintainers may suggest a different approach, and sometimes we may decide not to make the change. Either way, a clear issue is useful because it helps us understand how the project is being used.

## Open issues and implementation

An open issue is an invitation to discuss, investigate, or add useful context.

It does not necessarily mean that someone should start implementing the change right away.

Waiting for agreement first helps avoid situations where a contributor spends a lot of time on a solution that does not quite fit the project's direction.

When outside implementation would be helpful, a maintainer will say so explicitly.

We may also use labels such as:

- `help wanted`
- `implementation welcome`
- `good first issue`

If you are interested in implementing an issue, feel free to say so in the discussion.

## Pull requests

We generally do not review unsolicited pull requests.

Please start with an issue and wait until a maintainer has agreed that the change should be implemented and invited you to work on it.

A pull request is usually appropriate when:

1. the problem or proposed change has been discussed;
2. we have agreed on the general direction; and
3. a maintainer has invited you to implement it.

If you have been invited to submit a pull request, please:

- keep the change focused on the agreed issue;
- avoid unrelated refactoring or cleanup;
- include tests when behavior changes;
- update documentation when appropriate;
- explain non-obvious design choices;
- reference the relevant issue; and
- mention any important differences from what was previously discussed.

If the scope changes significantly while you are working, it is usually best to return to the issue and check in first.

Pull requests opened without prior discussion may be closed without a full code review. This is not a judgment on the quality of the work; it simply means we have not yet agreed to take on that change.

## Small fixes

Even small changes can sometimes have effects that are not obvious from outside the project, so the issue-first approach generally applies to small fixes too.

For very simple things, such as an obvious typo, reporting the location is already helpful. A maintainer may simply fix it directly.

There is no need to prepare a pull request just to make your contribution count.

## Good issue contributions

Some of the most valuable contributions do not contain code.

We especially appreciate:

- minimal bug reproductions;
- careful compatibility reports;
- investigations that narrow down the cause of a problem;
- examples of confusing or undocumented behavior;
- measurements and benchmarks;
- API usability feedback;
- real-world use cases;
- documentation gaps;
- accessibility findings; and
- testing of proposed fixes.

If you help us understand a problem better, that is a meaningful contribution.

## AI-assisted contributions

AI tools can be useful when investigating problems, preparing reproductions, or working on contributions.

If you use them, please make sure you personally review and understand what you submit.

In particular:

- verify that reported behavior is real;
- test reproduction steps yourself;
- verify technical claims before posting them;
- understand any code you submit;
- test proposed changes; and
- be prepared to discuss the contribution.

Please avoid submitting large numbers of unverified or speculative reports, since investigating them can take significant maintainer time.

## Security vulnerabilities

Please **do not report security vulnerabilities in public issues or pull requests**.

Use the project's private security-reporting mechanism instead.

If private vulnerability reporting is enabled on GitHub, use the repository's **Security → Report a vulnerability** option.

## Questions and early ideas

If GitHub Discussions is enabled, it is a good place for:

- general questions;
- early-stage ideas;
- design exploration;
- usage questions; and
- proposals that are not yet concrete enough for an issue.

Once a discussion identifies a specific problem or piece of work, it can move into an issue.

## Maintainer decisions

Not every valid issue will result in a code change.

Maintainers may decide not to pursue a proposal because:

- it is outside the project's scope;
- the maintenance cost is too high;
- the use case is very specialized;
- the behavior can already be achieved another way;
- it conflicts with compatibility requirements;
- the project is moving in a different direction; or
- it is simply not a current priority.

That does not mean the report was unhelpful.

Good issues give us useful information about how the project is being used, even when we decide not to make a change.

## Community expectations

Please keep discussions constructive, patient, and focused on the technical problem.

Maintainers may not always be able to investigate or respond immediately.

To help keep discussions manageable, please avoid:

- repeatedly asking for status updates;
- opening duplicate issues to attract attention;
- opening a pull request after being asked to wait;
- tagging individual maintainers unnecessarily; or
- privately contacting maintainers about ordinary project issues.

Keeping project discussions in public contribution channels also helps other users benefit from the context.

## A simple rule of thumb

If you find a problem:

**Show us the problem.**

If you have an idea:

**Explain the use case.**

If you know how you would solve it:

**Share your thinking in the issue.**

If outside implementation would be helpful:

**We will invite you to open a pull request.**

Thanks again for helping improve the project.
