# Integrated delivery-quality check (#40)

This is a **small evaluation of the existing Promise to Proof workflow**, not a new
production quality stage. It connects contract quality (#44), exact requirement
coverage (#41), material-risk verification (#42), review and stopping (#43), and
the independent review/proof judgments exercised by the existing #72 runner.

## Run on a supported live host

On macOS with an authenticated Codex CLI, Python 3.11+, Git, and the installed
`audit-acceptance` plus P2P delivery stage skills:

```sh
python3 checks/check_p2p_quality_integration.py --output-dir /absolute/new/integration-evidence
```

The directory must not exist yet. The test invokes the **existing audit skill**
twice before initiating any candidate verification. The source snapshots have
independent, authored expected outcomes: a complete proposed username contract
should be `READY_FOR_APPROVAL` (advice, not actual approval), while a source
that both accepts and rejects whitespace-only usernames must `BLOCKED`
pending a product decision. Both audits must cite exact source and contract
identities; contradictory source excerpts must come from the source itself.
Neither audit is permitted to change the source, proposal, Git index or product.

After these independent planning controls, the test reuses **six existing #72
fixed-candidate live fixtures**, keeping their expected verdicts and private
behavioral oracles outside the model input:

| Existing fixture | Integrated question |
|---|---|
| `review-meaningful-tests` | Do correct low-risk code, independent assertions and an optional suggestion pass without another test suite? |
| `green-but-incomplete` | Do green incomplete tests still fail the missing whitespace obligation R2? |
| `unrelated-scope-expansion` | Does review block unrelated fee changes, even when promised behavior passes proof? |
| `review-overmocked-boundary` | Does review reject a test that mocks away the production validator? |
| `verification-durable-control` | Does a consequential durable/concurrent booking seam receive meaningful restart and competing-process observations? |
| `review-reconcile-corrected-finding` | After a narrow R2 repair, are fresh independent review and proof bound to the exact changed candidate, with checked previous observations and retained prior findings? |

Each run uses the existing pinned delivery skill bundle, isolated product
generations, two distinct independent review/proof sessions and the fixed
comparison base. The integration checks requirement coverage, implementation
and evidence links, real saved review scope (including inspected blob identities),
material risk facts, private public-interface oracle results, the host sessions,
the exact retained candidate Git objects, and applicable previous observations.
It also checks that the ordinary delivery controller still completes without a
new mandatory stage. No child regression suite is reimplemented.

## One compact, inspectable outcome

The new `quality-integration.json` references the existing #72 per-fixture
`summary.json`, saved stage reports and real host receipts. It gives the exact
source/contract SHA-256 identities, pinned instruction identity, comparison
base, current product candidate, expectation and observation for each stage,
reviewed-scope digest, check commands, proof assertions, and pass/fail reasons.

A **PASS** requires all selected live audits and cases to pass. **FAIL** retains
the precise mismatch; **UNAVAILABLE** means the environment cannot establish
real live-host evidence. There is no mocked fallback and no claim that a
successful JSON/schema check alone proves model quality.

The deterministic CI regression is:

```sh
python3 -m unittest discover -s checks -p 'test_p2p_quality_integration.py' -v
```

It checks fixture selection, contradiction detection, exact source preservation,
stage binding, returned scope, stored evidence, stale-candidate refusal, and
normal controller completion using clearly labeled offline host fixtures.
**It cannot substitute for a live Codex run.**

## Limits

The initial live runner evaluates the source-audit and fixed-candidate
review/proof portions of the chain. It is *not* an autonomous planning-to-PR
delivery run: the candidate product bytes are deliberately preselected and
human-authored, not generated by an implementation worker. The separate offline
normal-controller scenario tests implementation and stage orchestration but
cannot demonstrate model decisions.

The suite does not guarantee defect-free software, evidence authenticity,
universal reliability, faster delivery or automatic #73 applicability. Its
purpose is to catch a bounded set of false completion and false-blocking
judgments without creating a second workflow. Ordinary authorization,
publication, merge gates and current-target compatibility remain unchanged.
