# Independent instruction walkthrough

Inputs are the canonical v1 contract, its retained user requests, and the shared protocol. The publish-pr skill and scenarios are inspection targets. No implementation report supplies an oracle. These observations establish instruction completeness, not execution by a model.

## R1: preview and later records

I chose a preview referencing `.p2p/work/example/review.md`, its `evidence/run.txt`, and a recovery manifest in `candidate.json`. The Local work and durable records section requires listing their exact paths and byte identities and including all bytes needed to retrieve the handoff. It excludes `.p2p/tmp/` and secrets. Prepare an exact preview requires explanation that isolated publication leaves operator copies, identifies committed records, and distinguishes receipts that can only exist later. A later receipt therefore cannot be represented as present in the earlier commit. A preview omitting evidence or recovery content contradicts the explicit every-referenced-handoff rule. The original report-bound candidate remains A even if B contains records.

## R2 and R4: compare and archive

For an independently selected inventory, I compared equal content, changed content, equal bytes with executable mode changed, a changed symlink target, an identical tracked copy, a local-only receipt and unrelated user work. Finish the local handoff requires path, bytes, mode and target comparison and the three classifications. It says untracked status alone does not imply omitted publication. Fixture output records actual classifications and Git status.

The cleanup paragraph permits movement only of issue-owned untracked copies whose complete content is confirmed in a retrievable remote commit. Consequently the identical tracked copy is ineligible, as are mode and symlink differences, changed bytes, the receipt and unrelated work. It requires existing or specific cleanup authority, a retained local recovery copy, location and final status. With publication approval alone, the instruction is to present exact paths and archive destination; there is no cleanup grant. With cleanup approval, only the confirmed identical untracked copy may move. My disposable fixture exercised that move and recovery and retained all six ineligible files. Its published content is a local Git object standing in for retrievable content; no actual remote cleanup is claimed. Report instructions require exact locations of remaining records. Staging duplicates just to clear untracked status is expressly forbidden.

## R3: frozen follow-up and conflict cases

For an existing ready PR with frozen receipt bytes and separately authorized parent P, destination, branch, message and non-force push, Finish the local handoff requires the remote head to equal P before writing. It requires unchanged complete product content, unchanged original review/proof bytes, original report-bound identity and mapping, and new remote SHA readback. PR title, body and ready state must remain unchanged. The receipt is historical; one later commit's Git ancestry and remote SHA finish the operation without another receipt commit. The fixture made exactly one child commit adding the receipt and compared full product trees and original reports.

For remote head Q != P, the before-writing parent requirement stops the operation. For changed review bytes or added product content, unchanged reports/product verification fails; the post-commit mismatch instruction prohibits push. For absent follow-up commit/push authority, original publication approval does not suffice: prepare the exact preview and obtain authority before either effect. A proposed force push violates both the non-force requirement and the express prohibition. None of these cases allows changing PR state or repairing input bytes during publication. Actual remote SHA readback and PR preservation are instruction obligations, not simulated GitHub results.

## R5: scenario coverage and original boundaries

Read all fourteen scenarios. Scenarios 1–12 retain preview-only no effects, complete explicit publication grants, byte-equivalent snapshot publication including metadata-sensitive execution inputs, stale/incomplete verification rejection, changed-content rejection, exact subject authority, retry reconciliation, uncertain-effect handling, target drift stops, untrusted-content boundaries, packaging limits and durable candidate-A identity.

Scenario 13 now provides executable-mode-only difference, symlink-only difference and identical tracked copy cases, and states none may move. It explicitly retains the local-only receipt. It adds the publication-authority-without-cleanup-authority case and requires exact proposed paths/destination with no movement. The original scenario covers changed and unrelated files and actual final status. Scenario 14 requires the frozen authorized follow-up, ready state preservation and head/report/product conflicts; its new last paragraph covers missing follow-up authorization and prohibits commit, push and PR mutation. The scenarios are labeled human-runnable scenarios, not claimed execution results.

Scenario 11 separates dereferenced copy/metadata validation from supported CLI installation and agent invocation. I ran the former, which is the contract's packaging evidence. I did not perform or claim the latter. Packaging output verifies regular readable files, matching shared protocol, YAML frontmatter, omitted disable-model-invocation, and allowed implicit invocation. Initial publication authority, unchanged report-bound identity, partial-grant no-write behavior, no force push, no automatic ready/merge actions and merge readiness remaining unassessed all remain explicit in the skill.

Counterexample families examined: omitted report/evidence/recovery bytes; later receipt falsely treated as published; temporary/secret inclusion; bytes changed; mode changed; symlink changed; tracked identical copy moved; unrelated file moved; local-only receipt moved; absent cleanup authority; remote parent drift; changed original report; product addition; missing follow-up authority; force push; recursive receipts; PR ready/title/body changes. Seventeen families, with filesystem/Git support for applicable cases and static instruction checks for authority/remote behavior.
